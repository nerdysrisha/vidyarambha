Manage Governance via Azure Policy AZ-104

Governance means keeping a growing cloud tidy and safe. Tags label things, Azure Policy sets the rules, and locks stop accidents.

Part 1

Notes

The problem

  • Contoso's cloud grew fast. An audit found many resources with no owner, project or cost center.
  • Finance cannot split the bill. Nobody knows who can switch a server off.
  • Plan: tag everything, force tags on new resources, fix old ones, protect the important ones.

Three guards, three jobs

  • RBAC is about people: who can do what.
  • Policy is about resources: what settings are allowed, even for an Owner.
  • Locks block delete or change, even for an Owner.
  • Policy is checked before a resource is made. RBAC and locks protect it afterwards.

Tags

  • A tag is a name and value pair on a resource, like CostCenter = CC-4021.
  • Used for cost reports, owners, projects, environments, sunset dates.
  • Not inherited. A tag on a resource group does not reach its resources by itself.
  • Tag names are not case sensitive. Tag values are.
  • Up to 50 tags per resource. Not every resource type supports tags.
  • Real examples: Owner = anna@contoso.com, Environment = prod, Project = payments.

Azure Policy

  • Definition: the rule. "If this is true, then do this effect."
  • Assignment: a definition applied to a scope. It flows down: management group > subscription > resource group. You can exclude some resources.
  • Initiative: a bundle of policies assigned together.
  • Many built-in definitions exist. You can also write your own.
  • Takes about 5 to 10 minutes to start working after you assign it.

Policy effects

  • Deny: block the request.
  • Audit: allow it, but mark it non-compliant.
  • Modify / Append: change properties or tags while creating or updating.
  • DeployIfNotExists: deploy a missing extra resource, such as diagnostic settings.
  • Disabled: switched off.

Fixing old resources: remediation

  • Policy only checks new or changed resources, plus a regular scan (about every 24 hours).
  • Old resources are just marked non-compliant. Nothing changes by itself.
  • A remediation task fixes them. Works for Modify and DeployIfNotExists.
  • Needs a managed identity to make the change. The portal creates it for you.

Resource locks

  • Delete (CanNotDelete): can read and change, cannot delete.
  • Read-only: can read only. No change, no delete. Can break things, for example listing storage keys.
  • Set on a subscription, resource group or resource. Child resources inherit the lock.
  • Applies to everyone, including Owners. To delete, remove the lock first.
  • Real example: Delete lock on rg-network-hub and on the production database.

More real-world policies

  • Allowed locations: only West Europe and North Europe, for data residency.
  • Allowed VM sizes: block expensive sizes in dev subscriptions.
  • Require tags: every resource must have Owner and CostCenter.
  • Audit: list VMs that have no backup.
Part 2

Exercise

Goal: tag a resource group, force and inherit the tag with policy, then lock the group. About 30 minutes.

The original steps use az104-rg2, the tag Cost Center with value 000, and rg-lock. Any names work. Real-world names are used here.

Task 1: Create a resource group with a tag

  1. Azure portal → search Resource groups → + Create.
  2. Name: rg-payments-prod. Region: East US (or your own).
  3. Next to the Tags tab. Name: CostCenter, value: CC-4021.
  4. Review + Create → Create.

Check: the group is listed, and its Tags page shows the CostCenter tag.

Task 2: Enforce the tag (Deny)

  1. Search Policy → Authoring → Definitions. Browse, then search Require a tag and its value on resources and open it.
  2. Assign policy. Scope: your subscription and rg-payments-prod.
  3. Basics: name Require CostCenter tag on payments resources. Policy enforcement: Enabled.
  4. Parameters: tag name CostCenter, tag value CC-4021.
  5. Remediation: leave Create a Managed Identity unticked. Review + Create → Create. Wait 5 to 10 minutes.
  6. Test it: Storage accounts → + Create. Resource group rg-payments-prod, a globally unique name like stpayments plus numbers. No tag. Review → Create.

Check: you get Validation failed. The error says the deployment was disallowed by the policy. See Raw Error for the policy name.

Task 3: Inherit the tag (Modify)

  1. Policy → Assignments. Use the ... menu on the Task 2 assignment → Delete assignment.
  2. Assign policy. Scope: the same resource group.
  3. Definition: Inherit a tag from the resource group if missing. Name it Inherit CostCenter tag from resource group.
  4. Parameters: tag name CostCenter.
  5. Remediation: tick Create a remediation task. This uses the Modify effect, so a managed identity is needed.
  6. Review + Create → Create. Wait 5 to 10 minutes.
  7. Test it: create a storage account in the same group, again with no tag. This time validation passes. Create, then Go to resource.

Check: on the storage account's Tags page, CostCenter = CC-4021 was added for you. Tip: the portal's Tags page lists all resources with a given tag.

Task 4: Lock the group

  1. Open rg-payments-prod → Settings → Locks → Add.
  2. Name: lock-no-delete. Type: Delete. OK.
  3. Overview → Delete resource group. Type the group name and confirm.

Check: a notification says the delete was denied by the lock.

Cleanup: remove the lock first, then delete rg-payments-prod. You will not be able to delete the group while the lock is there.

Good to remember for the exam

  • Tags are name and value pairs. They are not inherited by default.
  • Policy controls resources. RBAC controls people. Policy still applies to Owners.
  • Assignment = definition + scope. It inherits down the scopes and can have exclusions.
  • Deny blocks. Audit only flags. Modify and DeployIfNotExists can be remediated.
  • Remediation tasks fix existing resources and need a managed identity.
  • Locks: Delete or Read-only. Inherited by children. Beat any user permission.
  • To delete a locked resource, remove the lock first.
Part 3

Test yourself

Try all the questions first. Then press Check answers at the bottom.

  1. What is the main difference between Azure Policy and RBAC?
  2. You tag rg-payments-prod with CostCenter = CC-4021. A new VM is created in it. Does the VM get the tag?
  3. Finance wants every resource to carry a CostCenter tag, and new ones without it must be blocked. Which effect?
    1. Audit
    2. Deny
    3. Disabled
    4. DeployIfNotExists
  4. Your policy was assigned last week. Today you find 40 old resources without the tag. Why were they not fixed, and what do you do?
  5. Which effect needs a managed identity for remediation: Deny or Modify?
  6. You assign a policy at a management group. Which scopes does it apply to?
  7. A security officer wants to stop anyone, including Owners, from deleting the production database. What do you use?
  8. What is the difference between a Delete lock and a Read-only lock?
  9. You assigned a new policy two minutes ago and a test deployment still succeeds. Is it broken?
  10. The company wants only West Europe and North Europe to be used. What type of policy is this, and what effect?
Check answers
  1. Policy controls resources (what settings are allowed). RBAC controls people (who can do which actions).
  2. No. Tags are not inherited by default. You need a policy such as "Inherit a tag from the resource group if missing".
  3. B (Deny). Audit only flags. Disabled switches the policy off.
  4. Policy only checks new or changed resources. Old ones are just marked non-compliant. Create a remediation task (with a Modify or DeployIfNotExists policy).
  5. Modify. It changes resources, so it needs a managed identity. Deny only blocks.
  6. All management groups, subscriptions, resource groups and resources below it, unless you set an exclusion.
  7. A Delete lock on the database (or its resource group). Locks apply to Owners too.
  8. Delete lock: can read and change, cannot delete. Read-only lock: can read only, no change and no delete.
  9. No. A new assignment can take 5 to 10 minutes to take effect. Test again later.
  10. The built-in Allowed locations policy, with the Deny effect.
