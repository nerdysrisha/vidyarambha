Implement Intersite Connectivity AZ-104

By default, two VNets cannot talk to each other. This topic covers how to connect them (peering), how to check the link (Network Watcher) and how to steer traffic (custom routes).

Virtual network peering

  • Peering connects two VNets so they act as one network for connectivity. VMs talk using private IPs.
  • Traffic stays on the Microsoft backbone. It does not cross the public Internet.
  • Works in the same region, across regions through global VNet peering, and across subscriptions.
  • Address spaces must not overlap.
  • Peering is two links, one on each VNet. The portal creates both when you add it. Status shows Connected only when both exist.
  • Peering is not transitive. If A peers with B and B peers with C, A still cannot reach C.

Peering link settings

  • Allow access to the peered VNet: on by default. Turn it off and the VNets stop talking.
  • Allow forwarded traffic: accept traffic that did not start in the peered VNet, for example traffic sent through an NVA.
  • Gateway transit / use remote gateway: lets one VNet share the other's VPN or ExpressRoute gateway. This is different from ordinary VNet peering and is relevant when on-premises connectivity is reached through a gateway.

Network Watcher: Connection troubleshoot

  • Tests whether a source (such as a VM) can reach a destination on a given port and protocol.
  • You set: source VM, destination VM, protocol (TCP), destination port (3389).
  • Result is Reachable or Unreachable.
  • Other ways to test: Run command on the VM, or RDP in and use Test-NetConnection.

Network Watcher diagnostics

  • IP flow verify checks whether a specific inbound or outbound flow is allowed or denied by the effective NSG rules. It is useful when connectivity exists but an NSG may be blocking the flow.
  • Network topology gives a visual view of the resources and network relationships in a region, helping you spot missing or unexpected connections.
  • NSG diagnostics should be separated from connectivity-path testing: Connection troubleshoot tests reachability, while IP flow verification helps identify an NSG allow/deny decision.

NSG vs firewall

  • An NSG filters traffic at the network interface or subnet boundary using security rules and priorities. It is a distributed access-control layer.
  • An Azure Firewall is a managed, centralized firewall service that can inspect and control traffic as a network security appliance. A UDR can send traffic to it using next hop type Virtual appliance.
  • When troubleshooting, first establish the path with Connection troubleshoot, then inspect effective NSG rules/IP flow verification and any firewall policy that sits in the path.

Routes: system and custom

  • Azure creates system routes for every subnet automatically (VNet, Internet, peering).
  • A user-defined route (UDR), also called a custom route, adds to or overrides the system routes.
  • Routes live in a route table. The table only takes effect once associated with a subnet. It controls traffic leaving that subnet.
  • A route has: a destination (CIDR), a next hop type, and a next hop address.
  • Next hop types: Virtual appliance, Virtual network gateway, Virtual network, Internet, None.
  • Virtual appliance = an NVA (for example an Azure Firewall or another firewall appliance). Give its private IP as the next hop address. The NVA's NIC needs IP forwarding turned on.
  • Propagate gateway routes: if No, routes learned from a VPN or ExpressRoute gateway (BGP) are not added to this table.
  • Same destination as a system route? The UDR wins.

Part 2

Exercise

Goal: build two VNets with a VM each, prove they cannot talk, peer them, prove they can, then add a custom route. About 50 minutes.

1 Core VM + VNet2 Manufacturing VM + VNet3 Test (fails)4 Peer5 Test (works)6 Custom route

The original steps use CoreServicesVM, ManufacturingVM, CoreServicesVnet (10.0.0.0/16), ManufacturingVnet (172.16.0.0/16), az104-rg5 and similar. Any names and non-overlapping ranges work. Names here match topic 4.

Task 1: Create a core VM and VNet

  1. Portal → Virtual machines → Create → Azure virtual machine.
  2. Basics:
    • Resource group rg-intersite-eus (create new), name vm-core-01, region East US
    • Availability: No infrastructure redundancy required, security type Standard
    • Image Windows Server 2019 Datacenter: x64 Gen2, size Standard_DS2_v3
    • Username localadmin, a complex password, public inbound ports None
  3. Disks: take the defaults. Go to Networking.
  4. Virtual network → Create new: name vnet-core-eus, range 10.20.0.0/16, subnet snet-core 10.20.10.0/24 → OK. Replace any default values.
  5. Monitoring: Boot diagnostics → Disable.
  6. Review + create → Create. No need to wait. Start Task 2.

Task 2: Create a VM in a different VNet

  1. Repeat Task 1 with these changes:
    • VM name vm-mfg-01, same resource group, same region and settings
    • New VNet vnet-mfg-eus, range 10.30.0.0/16, subnet snet-mfg 10.30.20.0/24
  2. Boot diagnostics → Disable, then Review + create → Create.

Check: two VMs, in two VNets with different ranges. Wait until both are deployed and running before Task 3.

Task 3: Test the connection with Network Watcher

  1. Portal → Network Watcher → Connection troubleshoot.
  2. Source type Virtual machine → vm-core-01. Destination type Virtual machine → vm-mfg-01.
  3. Preferred IP version Both, protocol TCP, destination port 3389, source port blank, diagnostic tests default.
  4. Run diagnostic tests. It can take a couple of minutes.

Check: the connectivity test shows Unreachable. Expected, because the VMs are in different VNets.

Task 4: Peer the VNets

  1. Open vnet-core-eus → Settings → Peerings → + Add.
  2. Link names: vnet-core-to-vnet-mfg (this VNet) and vnet-mfg-to-vnet-core (remote VNet).
  3. Remote virtual network: vnet-mfg-eus in rg-intersite-eus.
  4. Leave Allow access selected on both sides, and select Allow forwarded traffic on both sides. Defaults for the rest.
  5. Add.
  6. On vnet-core-eus → Peerings, check the link and Refresh until status is Connected. Do the same on vnet-mfg-eus.

Check: both VNets list their peering link with status Connected.

Task 5: Test again with PowerShell

  1. Open vm-core-01 → Overview → Networking. Write down its private IP address.
  2. Open vm-mfg-01 → Operations → Run command → RunPowerShellScript.
  3. Run it with the core VM's private IP:
    • Test-NetConnection <vm-core-01 private IP> -port 3389
  4. Wait. The page shows Script execution in progress and can take a couple of minutes.

Check: the test succeeds (TcpTestSucceeded : True). Peering made the difference.

You could also RDP into a VM and run Test-NetConnection there, or rerun Network Watcher from Task 3.

Task 6: Create a custom route

  1. Add a subnet: vnet-core-eus → Subnets → + Subnet: name snet-perimeter, start 10.20.30.0, size /24 → Add.
  2. Route table: Route tables → + Create: group rg-intersite-eus, region East US, name rt-core, Propagate gateway routes No → Review + create → Create.
  3. Open rt-core (click the name, not the checkbox) → Settings → Routes → Add:
    • Route name to-core-via-nva, destination type IP Addresses
    • Destination 10.20.0.0/16 (the core VNet)
    • Next hop type Virtual appliance, next hop address 10.20.30.7 (the future NVA)
  4. Add.
  5. Associate: Subnets → + Associate: VNet vnet-core-eus, subnet snet-core.

Check: rt-core lists the route to-core-via-nva and shows snet-core under Subnets.

No NVA exists at 10.20.30.7 yet, so this only builds the plumbing. In real life, deploy the NVA and enable IP forwarding on its NIC first. Do Task 5 before this task, because the route sends traffic to an address with nothing behind it.

Cleanup: delete rg-intersite-eus when you finish. It removes everything built here.

Good to remember for the exam

  • Different VNets cannot communicate by default.
  • Peering gives private IP connectivity over the Microsoft backbone. It works across regions and subscriptions.
  • Peering needs non-overlapping address spaces and a link on each VNet. Status Connected means both exist.
  • Peering is not transitive.
  • Allow forwarded traffic is needed for traffic that passes through an NVA.
  • Network Watcher Connection troubleshoot tests a port between two VMs. Test-NetConnection does the same from inside a VM.
  • System routes exist by default. A UDR overrides them for the same destination.
  • A route table does nothing until it is associated with a subnet, and it affects traffic leaving that subnet.
  • Next hop Virtual appliance needs the NVA's private IP, and IP forwarding on the NVA's NIC.
  • Propagate gateway routes No keeps BGP-learned routes out of the table.

Test yourself

Try each question first. Press the button to show every answer under its question.

Check answersHide answers
  1. Two VMs sit in different VNets with no peering. Can they communicate by default?
    No. Resources in different VNets cannot communicate until you connect the VNets, for example with peering.
  2. You peer vnet-core-eus to vnet-mfg-eus but only one link exists. What status do you expect?
    Not Connected. Peering needs a link on each VNet. The portal creates both when you add the peering, and then both show Connected.
  3. VNet A is peered with VNet B, and VNet B is peered with VNet C. Can a VM in A reach a VM in C?
    1. Yes, peering is transitive
    2. Yes, but only on private IPs
    3. No, you must peer A and C directly or route through an NVA
    4. No, peering supports only two VNets in total
    C. Peering is not transitive. Peer A and C directly, or send traffic through an NVA with the right routes.
  4. Can you peer two VNets that both use 10.20.0.0/16?
    No. Peered VNets must have non-overlapping address spaces.
  5. Which Network Watcher tool did the lab use to test a TCP port between two VMs, and what did it show before peering?
    Connection troubleshoot (source VM, destination VM, TCP, port 3389). It showed Unreachable, because the VMs were in different VNets.
  6. The VMs have no public inbound ports, yet Test-NetConnection to port 3389 succeeds after peering. Why?
    The traffic is private, VM to VM across the peering. It is allowed by the default NSG rule that permits traffic from the VNet (peered VNets count as part of it). Public inbound ports only matter for Internet traffic.
  7. You need to send traffic from a subnet to a firewall appliance at 10.20.30.7. What do you build?
    A route table with a route to the destination range, next hop type Virtual appliance and next hop address 10.20.30.7, then associate the table with the subnet. The NVA's NIC also needs IP forwarding turned on.
  8. A UDR and a system route cover the same destination prefix. Which one is used?
    1. The system route
    2. The user-defined route
    3. Both, traffic is split
    4. Neither, the traffic is dropped
    B. A user-defined route overrides the system route for the same prefix.
  9. What does Propagate gateway routes: No do on a route table?
    Routes learned from a VPN or ExpressRoute gateway (BGP) are not added to the subnets that use this route table.
  10. You created rt-core with a route to an NVA, but traffic still takes the old path. What is the most likely cause?
    The route table is not associated with the subnet the traffic leaves from. A route table only works once associated with a subnet. (Also check that the NVA exists and has IP forwarding enabled.)
  11. Which Network Watcher feature is useful when you suspect an NSG rule is allowing or denying a particular flow?
    1. Network topology
    2. IP flow verify
    3. VNet peering
    4. Route table association
    B. IP flow verify checks a specific inbound or outbound flow against the effective NSG rules and reports whether it is allowed or denied.
  12. What is the difference between Connection troubleshoot and IP flow verify?
    Connection troubleshoot checks whether a source can reach a destination on a port/protocol. IP flow verify focuses on whether NSG rules allow or deny a particular flow.
  13. Why might a route use next hop type Virtual appliance with an address such as 10.20.30.7?
    The destination traffic is being steered through an NVA, such as a firewall. The appliance's private IP is the next hop, and IP forwarding must be enabled on its NIC.
  14. VNet A peers with VNet B and B peers with C. What does transitive mean here, and what should you do if A must reach C?
    VNet peering is not transitive: A does not automatically reach C through B. Peer A and C directly, or deliberately route traffic through an NVA/firewall with the required forwarded-traffic and routing configuration.
  15. What does Network Watcher's Network topology help you understand?
    It provides a visual view of network resources and their relationships, which can help identify unexpected or missing connectivity paths during troubleshooting.
  16. How is an NSG different from Azure Firewall in a troubleshooting scenario?
    An NSG provides distributed subnet/NIC-level traffic filtering through security rules and priorities. Azure Firewall is a centralized managed firewall service that can inspect and control traffic in the path. Check both when traffic crosses a firewall path and an NSG may also apply.
