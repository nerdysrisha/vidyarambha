Implement Network Traffic Management AZ-104

Spread incoming traffic across several VMs. The Load Balancer does it by IP and port (layer 4). The Application Gateway does it by looking at the web request itself (layer 7).

Load Balancer vs Application Gateway

  • Azure Load Balancer: layer 4 (TCP and UDP). Looks at IP address and port only. Fast and simple.
  • Application Gateway: layer 7 (HTTP and HTTPS). Can route by URL path or host header. Adds WAF (web application firewall), SSL termination and end-to-end encryption.
  • Both sit in front of a backend pool of VMs and spread the traffic across them.
  • Other options: Traffic Manager (DNS-based, global) and Front Door (global, layer 7).

Azure Load Balancer

  • Public load balancer: frontend has a public IP, used for Internet traffic. Internal (private) load balancer: frontend has a private IP only.
  • Three building blocks: frontend IP (where traffic arrives), backend pool (the VMs), rules (how to distribute).
  • A health probe checks each VM. A VM that fails the probe gets no new traffic.
  • A load balancing rule ties it together: frontend + port → backend pool + backend port, with a health probe.
  • Session persistence: None means no stickiness. A refresh can land on a different VM.
  • Standard SKU uses a static public IP and is closed to inbound traffic unless an NSG allows it.

Azure Application Gateway

  • Needs its own dedicated subnet, /27 or larger.
  • Parts: frontend IP (public, private or both), listener (protocol and port to listen on), routing rule, backend settings (how to talk to the backend), backend pools.
  • Path-based routing: the URL path picks the backend pool, for example /image/* to the image servers and /video/* to the video servers. Anything else goes to the default pool.
  • Backend settings include cookie-based affinity (sticky sessions) and connection draining (finish current requests before a server is removed).
  • Standard V2 tier gives all the layer 7 features. The WAF tier adds the firewall that checks for malicious traffic.
  • SSL/TLS termination: the gateway decrypts HTTPS at the listener (using a certificate), so the backend VMs can receive plain HTTP. For end-to-end TLS it re-encrypts to the backend. A Load Balancer does not do this; it passes TCP/UDP through untouched.
  • Check the pool with Backend health under Monitoring. Servers should show Healthy.

Part 2 · Exercise

Exercise

Goal: deploy the VMs from a template, put a Load Balancer in front of two of them, then put an Application Gateway in front of two of them with path-based routing. About 50 minutes.

1 Template: VNet + 3 VMs2 Load Balancer3 Application Gateway

The template creates the VM and network names (az104-06-vm0 and so on), so the lab names are kept on this page.

Task 1: Deploy the infrastructure from a template

  1. Download the Lab06 files: az104-06-vms-template.json and az104-06-vms-parameters.json.
  2. Portal → Deploy a custom template → Build your own template in the editor → Load file (template) → Save.
  3. Edit parameters → Load file (parameters) → Save.
  4. Resource group az104-rg6 (create new), enter a secure password.
  5. Review + Create → Create. Wait about 5 minutes.

Check: one VNet with three subnets, one VM in each, plus an NSG. If the VM size is unavailable, pick one with at least 2 cores.

Task 2: Configure the Load Balancer

  1. Portal → Load balancers → + Create. Basics:
    • Group az104-rg6, name az104-lb, same region as the VMs
    • SKU Standard, type Public, tier Regional
  2. Frontend IP configuration → Add: name az104-fe, IP type IP address, Public IP Create new:
    • Name az104-lbpip, SKU Standard, tier Regional, assignment Static, routing preference Microsoft network → Save twice
  3. Backend pools → Add: name az104-be, VNet az104-06-vnet1, configuration NIC. Add az104-06-vm0 and az104-06-vm1 → Add → Save.
  4. Review + create → Create → Go to resource.
  5. Settings → Load balancing rules → + Add:
    • Name az104-lbrule, IPv4, frontend az104-fe, backend pool az104-be
    • Protocol TCP, port 80, backend port 80
    • Health probe Create new: name az104-hp, TCP, port 80, interval 5 → Save
    • Session persistence None, idle timeout 4, TCP reset, floating IP disabled, outbound SNAT Recommended
  6. Save. Open Frontend IP configuration and copy the public IP address.
  7. Browse to that IP. Refresh a few times, or use an InPrivate window.

Check: the page alternates between Hello World from az104-06-vm0 and Hello World from az104-06-vm1.

Task 3: Configure the Application Gateway

  1. Subnet first: az104-06-vnet1 → Subnets → + Subnet: name subnet-appgw, start 10.60.3.224, size /27 (check the start address did not change) → Add.
  2. Portal → Application gateways → + Create. Basics:
    • Group az104-rg6, name az104-appgw, same region
    • Tier Standard V2, autoscaling No, instance count 2, HTTP2 disabled
    • VNet az104-06-vnet1, subnet subnet-appgw
  3. Frontends: type Public, public IP Add new: name az104-gwpip, zone 1 → OK.
  4. Backends: add three pools (each with targets, not empty):
    • az104-appgwbe: az104-06-nic1 (10.60.1.4) and az104-06-nic2 (10.60.2.4)
    • az104-imagebe: az104-06-nic1 only
    • az104-videobe: az104-06-nic2 only
  5. Configuration → Add a routing rule:
    • Rule az104-gwrule, priority 10, listener az104-listener, frontend Public IPv4, HTTP, port 80, listener type Basic
    • Backend targets tab: target az104-appgwbe, backend settings az104-http (create new)
    • Path-based routing → Add multiple targets. Add two rules:
      • Path /image/*, target name images, settings az104-http, backend az104-imagebe
      • Path /video/*, target name videos, settings az104-http, backend az104-videobe
  6. Next through Tags → Review + create → Create. Takes 5 to 10 minutes.
  7. Open az104-appgw → Monitoring → Backend health. Both servers should show Healthy.
  8. Copy the frontend public IP address from Overview. Browse to http://<ip>/image/, then http://<ip>/video/.

Check: /image/ shows the image server (vm1). /video/ shows the video server (vm2). Refresh or use InPrivate if you see old results.

Cleanup: delete az104-rg6 when you finish. The Application Gateway costs money while it runs.

Good to remember for the exam

  • Load Balancer = layer 4 (TCP/UDP). Application Gateway = layer 7 (HTTP/HTTPS).
  • Public LB has a public frontend IP. Internal LB has a private frontend IP only.
  • LB needs: frontend IP, backend pool, health probe, load balancing rule.
  • Failed health probe means the VM gets no new traffic.
  • Standard LB and Standard public IP: static address, closed to inbound traffic until an NSG allows it.
  • Application Gateway needs a dedicated subnet, /27 or larger.
  • Path-based and host-based routing, SSL termination and WAF are Application Gateway features.
  • WAF tier adds the firewall. Standard V2 does not have it.
  • Check Application Gateway pools in Backend health.

Test yourself

Check answersHide answers
  1. At which OSI layer does each service work: Azure Load Balancer and Azure Application Gateway?
    Load Balancer: layer 4 (TCP and UDP, by IP and port). Application Gateway: layer 7 (HTTP and HTTPS, can read the URL and headers).
  2. Name the parts you configure on a Load Balancer so that traffic reaches the VMs.
    A frontend IP configuration, a backend pool, a health probe, and a load balancing rule that links the frontend to the pool (for example TCP 80 to 80).
  3. You must send /image/* requests to one set of VMs and /video/* to another, behind one public IP. What do you use?
    1. Public Load Balancer
    2. Internal Load Balancer
    3. Application Gateway with path-based routing
    4. Network Watcher
    C. Only the Application Gateway reads the URL path. A Load Balancer sees only IP and port.
  4. What does the health probe do on a Load Balancer?
    It checks each backend VM (for example TCP port 80 every 5 seconds). A VM that fails the probe is taken out of rotation and gets no new traffic.
  5. What does the Application Gateway need in the VNet?
    A dedicated subnet of /27 or larger (the lab uses subnet-appgw, 10.60.3.224/27).
  6. The load balancing rule has Session persistence set to None. What does that mean when you refresh the page?
    There is no stickiness. Each new connection can go to any healthy VM, so the page can switch between vm0 and vm1.
  7. What is the difference between a public and an internal load balancer?
    A public load balancer has a public frontend IP and takes traffic from the Internet. An internal load balancer has a private frontend IP only and is used inside a VNet.
  8. You need a web application firewall and SSL termination in front of your web servers. Which service and tier?
    1. Load Balancer Standard
    2. Application Gateway, WAF tier
    3. Traffic Manager
    4. Public IP address
    B. The Application Gateway WAF tier adds the firewall that checks for malicious traffic. SSL termination is also an Application Gateway feature.
  9. Request A is http://<ip>/image/logo.png. Request B is http://<ip>/index.html. Where does each one go in the lab?
    A matches /image/* and goes to az104-imagebe (vm1). B matches no path rule, so it goes to the default target az104-appgwbe (vm1 and vm2).
  10. A Standard public Load Balancer is set up correctly, but nobody on the Internet can reach port 80. What do you check first?
    The NSG. Standard load balancers and Standard public IPs are closed to inbound traffic by default, so an NSG rule must allow port 80. Also check the health probe shows the VMs as healthy.
