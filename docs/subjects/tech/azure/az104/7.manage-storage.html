One storage account holds your blobs, file shares, queues and tables. This topic covers how to pick its redundancy, cut cost with tiers, protect the data, and lock down who can reach it.

Storage account basics

  • A storage account is a unique namespace for your data, reachable over HTTP or HTTPS from anywhere.
  • Holds four services: Blobs (unstructured data), Files (file shares), Queues (messages), Tables.
  • Name: globally unique, 3 to 24 characters, lowercase letters and digits only.
  • Performance: Standard for most apps, Premium for enterprise or high-performance workloads.
  • Soft delete keeps deleted data recoverable. Default retention is 7 days. You can also turn on versioning for blobs.

Left to right in cost: LRS, ZRS, GRS, GZRS. The lab picks GRS and ticks the read access box.

  • LRS: protects against a failed disk or rack. Not a whole datacenter.
  • ZRS: survives the loss of a datacenter or zone in the region.
  • GRS: also copies to a secondary region, protecting against a regional disaster. Secondary is not readable unless you add read access (RA-GRS).
  • See the primary and secondary locations under Data management → Redundancy.

A lifecycle rule moves blobs between tiers on its own, based on age.

  • Use Hot for data used often, Cool or Cold for infrequent access, Archive for rare access (offline, must be rehydrated before reading).
  • Moving or deleting a blob before the minimum days can cost an early deletion fee.
  • A lifecycle management rule sets scope, then conditions (such as days since last modified), then the action (move to cool, archive, delete).
  • You can also change a single blob's tier by hand with Change tier.

Blob containers and immutable storage

  • A container holds blobs, like a folder at the top level. Blob types: block (most files), append, page.
  • Public access level is Private (no anonymous access) by default. Opening the blob URL in a browser fails.
  • Immutable storage = WORM (write once, read many). Two policy types:
    • Time-based retention: blobs cannot be changed or deleted for the set period, for example 180 days.
    • Legal hold: blobs are locked until the hold is cleared. No fixed end date.
  • An unlocked retention policy can still be edited. A locked policy cannot be removed, and the period can only be extended.

Shared access signatures (SAS)

  • A SAS is a signed URL that gives limited access to a blob without sharing the account key.
  • You set: permissions (such as Read), start and expiry time, optional allowed IP addresses, and the signing key (Key 1).
  • Anyone holding the SAS URL gets that access until it expires.
  • Result in the lab: the plain URL fails, the Blob SAS URL shows the file.

Authorization: access keys, Entra ID and RBAC

  • Access keys: two account keys (Key 1, Key 2) give full control of the whole account. Keep them secret and rotate them; having two lets you rotate without downtime.
  • Microsoft Entra ID (RBAC): the recommended way. Assign roles such as Storage Blob Data Reader or Storage Blob Data Contributor to a user, group or managed identity. No key or SAS needed.
  • Management roles (such as Contributor) do not give access to blob data by themselves. Data access needs a data role.
  • Encryption: data is encrypted at rest by default with Microsoft-managed keys (you can use customer-managed keys), and in transit with HTTPS (secure transfer required).

A request must get through every layer, outside in.

  • Public network access has three settings: Disabled, Enabled from selected networks and IP addresses, Enabled from all networks.
  • To allow only a VNet: add a service endpoint Microsoft.Storage on the subnet, then add that VNet and subnet in the storage account's Networking page.
  • Private endpoint: gives the storage account a private IP address inside your VNet, so traffic stays on the Microsoft backbone. A service endpoint keeps the public address but limits access to your subnet. A private endpoint also works from on-premises over VPN or ExpressRoute.
  • Outside the allowed networks, you get not authorized to perform this operation, even in the portal's Storage browser.

Azure Files and Storage browser

  • Azure Files gives shared file storage in the cloud, organised in folders. Candidate to replace on-premises file shares.
  • File share tiers (standard accounts): Transaction optimized (default), Hot, Cool.
  • Storage browser is a portal tool to view and manage blobs, file shares, queues and tables in one place. You can add directories and upload files.
  • Files vs Blob: use Files when apps or users need a real file share with folders, mounted as a drive. Use Blob for unstructured data accessed by URL or API, such as images, backups and logs.
  • Protocols: Azure Files supports SMB (Windows, also Linux and macOS, port 445) and NFS (Linux, Premium). Make sure port 445 is open when mounting from on-premises.
  • Azure File Sync keeps an on-premises Windows Server in sync with an Azure file share. The server acts as a fast local cache, with cloud tiering for rarely used files.
  • Storage Explorer is a free desktop app to manage blobs, files, queues and tables. AzCopy is a command-line tool to copy data to, from or between storage accounts, signing in with Entra ID or a SAS.
  • Backup for the share is optional. The lab turns it off to keep things simple.

Exercise

Goal: create a GRS storage account, add a cost rule, make a protected blob container, share a file with a SAS, create a file share, then restrict the account to one VNet. About 50 minutes.

Task 1: Create and configure the storage account

  1. Portal → Storage accounts → + Create. Basics:
    • Resource group az104-rg7 (create new), unique name, region East US
    • Performance Standard, redundancy Geo-redundant storage
    • Tick Make read access to data available in the event of regional unavailability
  2. Advanced: take the defaults.
  3. Networking: Network access → Disable public access and use private access.
  4. Data protection and Encryption: read, keep the defaults (soft delete is 7 days).
  5. Review + Create → Create → Go to resource.
  6. Security + networking → Networking. Public network access is disabled. Change it to Enable from selected networks and IP addresses, tick Add your client IP address, Save.
  7. Data management → Redundancy: see the primary and secondary locations.
  8. Data management → Lifecycle management → Add a rule:
    • Name Movetocool → Next
    • Base blobs: if last modified more than 30 days ago, then Move to cool storage → Add

Check: the account shows GRS with a secondary location, public access limited to your IP, and the rule Movetocool is listed.

Task 2: Create and configure secure blob storage

  1. Container: Data storage → Containers → + Add container: name data, access level stays Private → Create.
  2. Retention policy: on the container, ellipsis (...) → Access Policy → Immutable blob storage → Add policy: type Time-based retention, 180 days → Save.
  3. Upload: open data → Upload, choose a small file, expand Advanced:
    • Blob type Block blob, block size 4 MiB, tier Hot
    • Upload to folder securitytest, default encryption scope
    Then Upload.
  4. Select the file and look at the options: Download, Delete, Change tier, Acquire lease.
  5. Try the plain URL: copy the URL from Properties, paste it in an InPrivate window.
  6. Generate a SAS: on the file, ellipsis (...) → Generate SAS:
    • Signing key Key 1, permissions Read
    • Start: yesterday, current time. Expiry: tomorrow, current time. Allowed IPs blank
    Generate SAS token and URL, copy the Blob SAS URL, open it in another InPrivate window.

Check: the plain URL shows an XML error (ResourceNotFound or PublicAccessNotPermitted), because the container is private. The SAS URL shows the file.

Task 3: Create and secure Azure Files

  1. Share: Data storage → File shares → + File share: name share1, tier Transaction optimized. On Backup, leave Enable backup unticked → Review + create → Create.
  2. Storage browser: open it → File shares → share1. Try + Add directory, then Upload a file.
  3. Create a VNet: Virtual networks → + Create: your resource group, name vnet1, defaults → Review + create → Create → Go to resource.
  4. Settings → Service endpoints → Add: service Microsoft.Storage, subnet Default → Add.
  5. Back on the storage account → Security + networking → Networking → Add existing virtual network: vnet1, subnet default → Add.
  6. In the Firewall section, delete your client IP address, then Save.
  7. Open Storage browser and refresh. Try your file share or blob content. It can take a couple of minutes to take effect.

Check: you now get not authorized to perform this operation, because your computer is not on vnet1.

Cleanup: delete az104-rg7 when you finish. It removes the storage account and the VNet.

Good to remember for the exam

  • A storage account holds blobs, files, queues and tables. The name is globally unique, 3 to 24 lowercase letters and digits.
  • LRS = one datacenter. ZRS = three zones in the region. GRS = adds a secondary region. Add RA to read the secondary.
  • Tiers: Hot, Cool, Cold, Archive. Archive is offline and needs rehydration.
  • Lifecycle management moves or deletes blobs automatically by age.
  • Containers are private by default. A plain URL to a private blob fails.
  • Immutable storage is WORM: time-based retention (fixed period) or legal hold (until cleared). A locked policy cannot be removed.
  • SAS = signed URL with limited permissions, start and expiry, and optional IP limit. No account key shared.
  • Restrict to a VNet: service endpoint Microsoft.Storage on the subnet, then add the VNet in the storage Networking page.
  • Soft delete is 7 days by default. Versioning is optional.

Test yourself

Try each question first. Press the button to show every answer under its question.

Check answersHide answers
  1. Which four services can one storage account hold?
    Blobs, Files, Queues and Tables.
  2. You want the lowest-cost option that survives the loss of a whole datacenter inside one region. Which redundancy?
    1. LRS
    2. ZRS
    3. GRS
    4. RA-GRS
    B. ZRS copies data across three zones in the region. LRS stays in one datacenter. GRS and RA-GRS cost more and are aimed at regional disasters.
  3. What is the difference between GRS and RA-GRS?
    Both copy data to a secondary region. With plain GRS you cannot read the secondary copy. With RA-GRS the secondary is readable at any time.
  4. Blobs that have not been modified for 30 days should move to Cool automatically. Where do you set that up?
    Data management → Lifecycle management → Add a rule: base blobs, last modified more than 30 days ago, then Move to cool storage.
  5. You paste the URL of a blob in a private container into an InPrivate browser window. What do you see, and why?
    An XML error such as ResourceNotFound or PublicAccessNotPermitted. The container's public access level is Private (no anonymous access).
  6. A partner needs to download one blob for the next 24 hours. You do not want to share the account key. What do you create?
    A shared access signature (SAS) for that blob with the Read permission and an expiry 24 hours from now. You can also limit it to the partner's IP address.
  7. A container has a time-based retention policy of 180 days. What happens when someone tries to delete a blob after 10 days? What is the other policy type?
    The delete is blocked. Blobs are WORM (write once, read many) for the retention period. The other type is a legal hold, which stays until it is cleared.
  8. You want a storage account reachable only from one VNet subnet. What do you do?
    1. Add a service endpoint Microsoft.Storage on the subnet, then add the VNet and subnet in the storage account's Networking page
    2. Peer the VNet with the storage account
    3. Add a route table to the subnet
    4. Create a SAS token
    A. The service endpoint plus the VNet rule in the storage firewall. Peering is between VNets, a route table steers traffic, and a SAS is authorization, not network access.
  9. After you restrict the account to vnet1 and delete your client IP, Storage browser in the portal says not authorized to perform this operation. Why?
    Your computer is not in the allowed VNet and your IP is no longer in the firewall, so the network rules block the request.
  10. What is the default soft delete retention for blobs, and what does soft delete give you?
    7 days. A deleted blob stays recoverable during that time.
