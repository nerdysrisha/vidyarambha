Azure App Service is a managed platform for hosting websites and APIs without managing servers. This topic covers the plan that sets your compute, deployment slots for safe releases, pulling code from Git, and scaling when traffic grows.

App Service basics

  • Azure App Service is a PaaS for web, mobile and API apps. Azure runs the OS, patching and load balancing. You bring the code.
  • A web app is the app itself. It runs on an App Service plan, which sets the region, OS, size, features and price.
  • Several apps can share one plan, and then they share the same compute.
  • Publish: Code (pick a runtime) or Container. Runtime stack examples: PHP, .NET, Java, Node, Python.
  • Operating system: Linux or Windows. It is chosen at creation and the plan is tied to it.
  • Default URL: <name>.azurewebsites.net. The web app name must be globally unique.
  • App Service vs VM: App Service is PaaS, so Azure manages the OS, patching, runtime and built-in scaling. A VM is IaaS: you manage the OS and everything on it, but get full control. Choose App Service for standard web apps and APIs, a VM when you need custom software or OS-level access.
  • Application settings (under Settings → Environment variables) are key-value pairs passed to the app as environment variables, for example connection strings. They override values in the code's config files and are kept out of the source code.
  • Custom domain: map your own name (for example www.contoso.com) with a CNAME or A record in DNS, then verify it on the web app. Needs Basic tier or higher.
  • TLS/HTTPS: the default azurewebsites.net address already has HTTPS. For a custom domain, add a certificate (App Service managed certificate or your own) and create a TLS/SSL binding. Turn on HTTPS Only to redirect HTTP to HTTPS, and set the minimum TLS version.
  • Scenario in the lab: an on-premises PHP site on ageing hardware moves to Azure to avoid new hardware costs.

Pricing plans (tiers)

Cheaper, fewer features → costlier, more features
Free / Shared→Basic→Standard→Premium V3→Isolated V2
Where features start
Basic: custom domain, manual scale outStandard: slots, rules-based autoscalePremium: more slots, more instances

Free and Shared run on shared machines. Basic and up run on dedicated virtual machines. Isolated V2 is a private environment.

  • Deployment slots need Standard or higher. Standard allows 5 slots, Premium 20.
  • Scale out: Basic is manual (up to 3 instances). Standard adds rules-based autoscale. Premium allows the most instances.
  • The lab picks P1V3 so every feature in the exercise is available.

Deployment slots

Before the swap
Production: default pagestaging: Hello World
Swapwarm up staging, then switch the routing
After the swap
Production: Hello Worldstaging: previous production

Users never hit a half-deployed site. The old version stays in staging, so a second swap is an instant rollback.

  • A deployment slot is a live copy of the app with its own URL and its own settings.
  • Slots run on the same App Service plan, so they share its compute with production.
  • Typical use: deploy to staging, test it, then swap to production.
  • A swap warms up the source slot first, then switches. This avoids downtime and gives a quick rollback.
  • Clone settings from: copy configuration from another slot, or Do not clone settings (the lab choice, you get an empty slot).
  • Settings marked as deployment slot setting stay with the slot during a swap. Other settings move with the app.
  • Many teams use several slots, for example dev, QA, test and production.

  • Deployment Center connects the app to a source so code deploys continuously and the app always has the latest version.
  • Sources include GitHub, Azure Repos, Bitbucket, Local Git and External Git.
  • External Git needs a repository URL and a branch. The sample repo uses master.
  • Each slot has its own Deployment Center, so check which blade you are on.
  • The first deployment can take a minute. Refresh the page.

Scaling: up and out

Scale upbigger machinechange the plan size or tier
more CPU, memory, features
Scale outmore instancessame size, more copies
1 instance→2 instances→N instances

Scale up changes the plan. Scale out adds instances and is the one you automate.

  • Scaling applies to the App Service plan, so it affects every app and slot on it. In the portal it lives under Scale out (App Service plan).
  • Three scale out modes:
    • Manual: you set a fixed instance count.
    • Automatic: App Service adds and removes instances for you. You only set the Maximum burst (the lab uses 2).
    • Rules based: you define rules on metrics such as CPU, memory or bandwidth, with min, max and default instance counts.
  • Autoscaling keeps performance steady when traffic rises, and saves cost when it drops.

Load testing and diagnostics

  • Diagnose and solve problems has a Load Test your App box that creates an Azure Load Testing resource.
  • You add an HTTP request with your app URL (it must start with https://) and run the test.
  • Live metrics to watch: Virtual users, Response time, Requests/sec.
  • Test the production URL, so you see autoscale react.
Part 2 · Exercise

Exercise

Goal: create a Linux PHP web app, add a staging slot, deploy Hello World to it from GitHub, swap it into production, then turn on autoscale and load test it. About 20 minutes.

1 Web app2 Staging slot3 Deploy from Git4 Swap5 Autoscale + test

Lab names are kept: az104-rg9 and staging. Use any globally unique web app name. If the deployment fails, try another region, because quotas differ by region.

Task 1: Create and configure the web app

  1. Portal → App services → + Create → Web App. Basics:
    • Resource group az104-rg9 (create new), unique web app name
    • Publish Code, runtime stack PHP 8.2, operating system Linux
    • Region East US, pricing plan Premium V3 P1V3, zone redundancy default
  2. Review + create → Create. Wait about a minute.
  3. Go to resource.

Check: the web app is running on a P1V3 Linux plan in az104-rg9.

Task 2: Create a deployment slot

  1. On the web app, click the Default domain link to see the default page, then close the tab.
  2. Deployment → Deployment slots → Add slot: name staging, clone settings Do not clone settings → Add.
  3. Refresh the page. You see the Production and Staging slots.
  4. Select the staging slot and note that its URL differs from production.

Check: two slots are listed, and staging has its own URL.

Task 3: Configure deployment settings

  1. In the staging slot: Deployment Center → Settings. Make sure you are on the staging blade, not production.
  2. Source External Git. Repository https://github.com/Azure-Samples/php-docs-hello-world, branch master → Save.
  3. Staging slot → Overview → click Default domain to open it in a new tab. Refresh if needed.

Check: the staging URL shows Hello World. Production still shows the default page.

Task 4: Swap the slots

  1. Go back to Deployment slots → Swap.
  2. Review the defaults → Start Swap. Wait for the notification that the swap finished.
  3. Open App Services and select the web app (this is the production slot). On Overview, open the Default domain.
  4. Copy the production URL. You need it for the load test.

Check: the production URL now shows Hello World!.

Task 5: Configure and test autoscale

  1. On the production web app: Settings → Scale out (App Service plan).
  2. Scaling: Automatic (note the Rules Based option). Maximum burst 2 → Save.
  3. Diagnose and solve problems → Load Test your App → Create Load Test → + Create, give it a unique name → Review + create → Create → Go to resource.
  4. On Overview, under Create by adding HTTP requests, click Create.
  5. Test plan tab → Add request, paste the production URL (starts with https://) → Add.
  6. Review + create → Create. It can take a couple of minutes.
  7. Open the test and refresh. Watch Virtual users, Response time and Requests/sec.
  8. Click Stop. You do not need to wait for the run to finish.

Check: automatic scaling is saved with a maximum burst of 2, and the live metrics show the load test running against your site.

Cleanup: delete az104-rg9 when you finish. It removes the web app, plan, slot and load test. A P1V3 plan costs money while it exists.

Good to remember for the exam

  • The App Service plan sets region, OS, size, features and price. Web apps run on it and can share it.
  • Web app names are globally unique: <name>.azurewebsites.net.
  • Deployment slots need Standard or higher. Standard 5, Premium 20. Each has its own URL.
  • Slots share the plan's compute with production. Heavy testing in a slot can slow production.
  • Swap warms up the source and switches with no downtime. Swap again to roll back.
  • Settings marked deployment slot setting stay with the slot. The rest move with the app.
  • Deployment Center sets continuous deployment per slot: GitHub, Azure Repos, Bitbucket, Local Git, External Git.
  • Scale up = bigger plan. Scale out = more instances. Scaling applies to the whole plan.
  • Scale out modes: manual, automatic (set Maximum burst), rules based (metrics like CPU).
  • Load testing uses Azure Load Testing, started from Diagnose and solve problems.

Test yourself

Try each question first. Press the button to show every answer under its question.

Check answersHide answers
  1. What is the difference between a web app and an App Service plan?
    The web app is your application. The App Service plan is the compute behind it: it sets region, OS, size, features and price. Several apps can share one plan.
  2. You need deployment slots for a production web app. Which pricing plan is the lowest that supports them?
    1. Free
    2. Shared
    3. Basic
    4. Standard
    D. Slots start at Standard (5 slots). Premium allows 20. Free, Shared and Basic do not support slots.
  3. You create a staging slot with Do not clone settings. What does the slot contain, and what is its URL like?
    An empty slot with default settings and no code. It gets its own URL, different from production, for example <name>-staging.azurewebsites.net.
  4. You want a slot to pull code from a GitHub repository on every push. Where do you set that up?
    In that slot's Deployment Center → Settings. Pick the source, repository and branch. Each slot has its own Deployment Center.
  5. The staging slot shows Hello World and production shows the default page. You swap. What does each slot show afterwards?
    Production shows Hello World. Staging now holds the previous production content (the default page). Swapping again would roll back.
  6. Why does a swap normally cause no downtime?
    App Service warms up the source slot first, then switches the routing between the slots. Users keep hitting a running app.
  7. A connection string must always stay with the staging slot and never move to production on a swap. What do you do?
    Mark the setting as a deployment slot setting. Slot settings stay with the slot, other settings swap with the app.
  8. A team runs heavy tests in a staging slot and production gets slower. Why?
    1. Slots share the App Service plan's compute with production
    2. Slots use a separate, smaller plan
    3. Swap copies the load to production
    4. Staging slots disable autoscale
    A. All slots of an app run on the same plan, so they compete for the same CPU and memory.
  9. What is the difference between scale up and scale out?
    Scale up moves the plan to a bigger size or tier (more CPU, memory, features). Scale out adds more instances of the same size. Autoscale is a scale out feature.
  10. In the lab you choose Automatic scaling with Maximum burst 2. What does that mean, and what is the alternative?
    App Service adds instances for you as needed, up to 2. The alternative is Rules based scaling, where you define metric rules (CPU, memory, bandwidth) and instance limits yourself. A third option is manual, with a fixed count.
  11. You scale out the plan to 3 instances. Which apps are affected?
    Every app and slot on that App Service plan, because scaling applies to the plan, not to one app.
  12. Where do you start a load test for your web app, and which URL should you test?
    Diagnose and solve problems → Load Test your App → Create Load Test (Azure Load Testing). Use the production default domain URL, starting with https://, so you can see autoscaling react.
