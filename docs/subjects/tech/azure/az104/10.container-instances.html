Azure Container Instances AZ-104

Azure Container Instances (ACI) runs a container in Azure with no server to build or manage. You point it at an image, give it a DNS name, and it is online in a couple of minutes. This topic covers containers, container groups, networking, restart policies and how ACI differs from Web Apps and AKS.

Containers and Docker

Containerlight: shares the host OS kernel
App + librariesContainer runtimeHost OSHardware

A container packages the app and what it needs, without a guest OS. It starts in seconds and is small.

  • Docker is a platform to package and run apps in isolated environments called containers.
  • An image is the read-only template. A container is a running copy of an image.
  • Images are stored in a registry: Azure Container Registry, Docker Hub or another registry.
  • Scenario in the lab: a web app on an on-premises VM moves to the cloud, with no fleet of servers to manage.

What ACI is

  • ACI is a serverless way to run containers on Azure. No VMs to provision, patch or scale.
  • Runs Linux and Windows containers.
  • You choose the CPU and memory for the container. Billing is per second for what you allocate, and only while it runs.
  • Starts fast, so it suits short-lived or bursty work: a simple web app, a build job, a batch task, a quick test.
  • Workloads are usually started and stopped by some process or trigger.
  • Not the best fit for large apps that need orchestration, rolling updates or autoscaling. That is AKS or App Service.

Container groups

shared lifecycleshared network + IPshared volumes
Container 1web front endport 80
Container 2sidecarlogging, sync

Containers in a group talk to each other over localhost. Multi-container groups are Linux only.

  • A container group is a collection of containers on the same host. It is the top-level ACI resource, like a pod in Kubernetes.
  • They share the lifecycle, the network (one IP, one DNS label, ports must not clash) and storage volumes.
  • The lab creates a group with a single container. Portal deployments of several containers or YAML templates are used for bigger groups.
  • Multi-container groups work with Linux containers only. Windows groups have a single container.

Image source

  • Quickstart images: Microsoft samples. The lab uses mcr.microsoft.com/azuredocs/aci-helloworld:latest (Linux).
  • Azure Container Registry: your own private images.
  • Other registry: Docker Hub or any registry, public or private (with credentials).
  • The image name ends with a tag such as :latest.

The FQDN always follows the pattern label.region.azurecontainer.io.

  • Networking type: Public (an IP address and optional DNS label), Private (inside a virtual network) or None.
  • The default exposed port is 80 (TCP). You can add other ports.
  • The DNS name label must be unique in the region. If you get DNS name label not available, pick another.
  • The label is optional. Without it you only get the public IP address.

Restart policy, variables and storage

  • Restart policy: what ACI does when the container stops.
    • Always (default): restart it every time. Fits long-running apps such as a web server.
    • On failure: restart only if it exits with an error.
    • Never: run once. Fits batch and task jobs.
  • Environment variables: pass settings to the app. Mark one as secure to hide its value (for passwords and keys).
  • Storage: container storage is lost when the container stops. For data that must survive, mount an Azure Files share. Other volume types: empty directory, secret, cloned Git repo.
  • These settings sit on the Advanced tab (restart policy, variables, command override).

Monitoring and logs

  • The Monitoring tab can send container instance logs to a Log Analytics workspace. The lab turns it off to keep things simple.
  • Without that, you can still read the container's live output in the portal: Settings → Containers → Logs.
  • The same Containers page has Events and Connect (open a shell inside the container).
  • The sample app logs each HTTP GET request, so refreshing the page creates entries.
  • The Overview blade shows the Status (Running) and the FQDN.

ACI, Web Apps or AKS?

Less to manage → more control
Web Apps (code or container)→ACI (single containers)→AKS (orchestrated fleet)

A rough guide for the exam. All three can run containers.

  • ACI: simple, short-lived or bursty containers, quick tests, jobs. No orchestration.
  • App Service: web apps with slots, autoscale and a custom domain. It can also run a container image.
  • AKS: many containers that need scaling, service discovery and rolling updates.

Exercise

Goal: deploy a sample web container to ACI from a Quickstart image, open it in a browser, and read its logs. About 15 minutes.

1 Deploy the container2 Test and read logs

Lab names are kept: az104-rg9 (the same resource group as the Web Apps lab) and az104-c1. Use any valid, unique DNS name label.

Task 1: Deploy a container instance from a Docker image

  1. Portal → Container instances → + Create. Basics:
    • Resource group az104-rg9 (create new if needed), container name az104-c1
    • Region East US (or one near you)
    • Image source Quickstart images, image mcr.microsoft.com/azuredocs/aci-helloworld:latest (Linux)
  2. Next: Networking: set a DNS name label that is unique. The site will be at label.region.azurecontainer.io. Change the label if you get DNS name label not available.
  3. Next: Monitoring: untick Enable container instance logs.
  4. Next: Advanced: just review, no changes.
  5. Review + Create, check validation passed, Create. Wait 2 to 3 minutes.

While you wait, you can look at the app's code in the GitHub repo Azure-Samples/aci-helloworld, in the app folder.

Check: the deployment completes without errors.

Task 2: Test and verify the deployment

  1. Go to resource. On Overview, check that Status is Running.
  2. Copy the FQDN, open a new browser tab and go to that address. It is served on port 80.
  3. You should see Welcome to Azure Container Instance. Refresh several times to create log entries, then close the tab.
  4. Back in the portal: Settings → Containers → Logs.
  5. Look for entries that show the HTTP GET requests from your browser.

Check: the welcome page loads from the FQDN, and the logs list your GET requests.

Cleanup: delete az104-rg9 when you finish (select the resource group, Delete the resource group, type its name, Delete, confirm). If you did the Web Apps lab in the same group, this removes that too. CLI: az group delete --name az104-rg9.

Good to remember for the exam

  • ACI = serverless containers. No VMs to manage. Billed per second for the CPU and memory you allocate.
  • Runs Linux and Windows containers. Multi-container groups are Linux only.
  • A container group shares host, lifecycle, network (one IP, one DNS label) and volumes.
  • FQDN pattern: label.region.azurecontainer.io. Default port 80. The label must be unique in the region.
  • Restart policy: Always (default), On failure, Never (for run-once jobs).
  • Container storage is not persistent. Mount an Azure Files share to keep data.
  • Secure environment variables hide secrets such as passwords.
  • Images come from Quickstart samples, Azure Container Registry or another registry.
  • Logs: Containers → Logs in the portal, or send them to Log Analytics.
  • Best for simple, short-lived or bursty work. Use AKS when you need orchestration.
Part 3

Test yourself

Try each question first. Press the button to show every answer under its question.

Check answersHide answers
  1. What does "serverless" mean for Azure Container Instances?
    You do not provision, patch or scale any VM or host. You give ACI an image and CPU and memory, and Azure runs it. You pay per second only while it runs.
  2. What is the difference between a Docker image and a container?
    An image is the read-only template that holds the app and its dependencies. A container is a running instance created from that image.
  3. You want to run a container from your own private images. Which image source do you pick?
    1. Quickstart images
    2. Azure Container Registry
    3. An ARM template
    4. A Log Analytics workspace
    B. Azure Container Registry holds your private images. Quickstart images are Microsoft samples. The others are not image sources.
  4. You deploy with DNS name label mysite in East US. What address do you use?
    mysite.eastus.azurecontainer.io, served on port 80 by default. If you get DNS name label not available, the label is already used in that region, so choose another.
  5. What is a container group, and what do its containers share?
    A collection of containers scheduled on the same host, and the top-level ACI resource. They share the lifecycle, the network (one IP address and DNS label, so ports must not clash) and storage volumes.
  6. You need a group with a web container plus a logging sidecar container. Which operating system must you use?
    1. Windows
    2. Linux
    3. Either one
    4. Neither, ACI allows one container only
    B. Multi-container groups are supported for Linux containers only. Windows groups hold a single container.
  7. A batch container should run once and not restart when it finishes. Which restart policy?
    Never. Always is the default and suits long-running apps. On failure restarts only after an error exit.
  8. The container writes files to its local disk. After it is restarted, the files are gone. How do you keep them?
    Mount an Azure Files share as a volume. Container local storage is not persistent.
  9. How do you pass a database password to the container without showing it in the portal?
    Add it as an environment variable and mark it secure. Its value is hidden from the portal and the API.
  10. The container is Running and you opened the FQDN a few times. Where do you see the HTTP GET requests?
    Settings → Containers → Logs on the container instance. You can also send logs to Log Analytics by enabling container instance logs on the Monitoring tab.
  11. Which service would you pick for a few simple, short-lived containers, versus many containers needing orchestration?
    ACI for simple, short-lived or bursty containers. AKS when you need orchestration, scaling and rolling updates across many containers.
