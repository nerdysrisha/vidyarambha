Azure Monitor: Logs, Alerts and Action Groups AZ-104

Azure Monitor collects data from your Azure resources, stores it, and tells you when something happens. In this topic a VM sends data to a Log Analytics workspace, you query it with KQL, and you build an alert that emails the team when the VM is deleted. This covers metrics, logs, the Activity Log, action groups and alert processing rules.

Azure Monitor and its data

  • Azure Monitor is the platform to collect, analyze and act on data from Azure, on-premises and other clouds.
  • Metrics: numbers over time (such as CPU %). Light, near real time, kept 93 days.
  • Logs: detailed records stored in a Log Analytics workspace and queried with KQL (Kusto Query Language).
  • Activity Log: subscription-level record of who did what to a resource (create, delete, change). Kept 90 days. Not a metric.
  • Host metrics being visible does not prove logs-based VM monitoring is set up. You need the agent, a rule and a workspace.
  • Metrics vs logs: use metrics for fast numeric checks and simple alerts (is CPU high now?). Use logs for detail and analysis across many resources (what happened, and why?). Metrics come automatically from Azure resources. Logs must be sent to a workspace first.
  • Diagnostic settings (on a resource) send its platform logs and metrics to a destination: a Log Analytics workspace, a storage account (archive), Event Hubs or a partner solution. The Activity Log has its own diagnostic setting to keep it longer than 90 days.

Collecting VM data: agent, DCR, workspace

AMA on VM→ DCR association →DCR→Log Analytics workspace

No data collection rule association, no data in the workspace.

  • Azure Monitor Agent (AMA) runs on the VM as an extension. On Windows it is AzureMonitorWindowsAgent. Check it shows Provisioning succeeded.
  • A Data collection rule (DCR) says what to collect and where to send it. It must be associated with the VM.
  • A Log Analytics workspace is the store. Data can take several minutes to arrive.
  • Useful tables: Heartbeat (the agent says "I am alive") and InsightsMetrics (performance counters).
  • Deleted VM = no new data, but data already collected stays for the workspace retention period.

KQL basics

  • A query starts with a table, then pipes (|) steps: where (filter), summarize (group or count), bin() (time buckets), render (chart).
  • ago(30m) means "the last 30 minutes". =~ compares text ignoring case.
  • Open it from the workspace: General → Logs (KQL mode).
  • Pattern: filter first, then aggregate. For example InsightsMetrics | where Name == "UtilizationPercentage" | summarize avg(Val) by bin(TimeGenerated, 5m) gives average CPU per 5 minutes. Heartbeat | summarize max(TimeGenerated) by Computer shows the last time each VM reported in.

Alerts

  • An alert rule has: scope (what to watch), condition (signal and logic), actions (action group) and details (name, resource group, severity).
  • Alert types: Metric, Log search (KQL), Activity Log (and others such as service health).
  • Deleting a VM is an Activity Log administrative operation: Microsoft.Compute/virtualMachines/delete. It is not a VM metric.
  • Scope here is the subscription, so any VM deletion in it triggers the alert. Activity Log alerts have a Global region.
  • Severity runs from 0 (Critical) to 4 (Verbose).
  • Metric alert example: signal Percentage CPU, aggregation Average, operator Greater than, threshold 80 (percent), checked every 1 minute over the last 5 minutes. When true, it fires and runs the action group. Static thresholds are fixed numbers. Dynamic thresholds learn the normal pattern.
  • Log alert: runs a KQL query on a schedule and fires on the result, for example when the number of rows is above a threshold. Costs more than a metric alert and has a delay, but can check anything in the logs.

Action groups

  • An action group is a reusable list of who gets notified and what runs when an alert fires.
  • Notifications: Email, SMS, push (Azure app) and voice.
  • Actions: Automation runbook, Azure Function, Logic App, webhook, ITSM, Event Hub.
  • Lab values: name Alert the operations team, display name AlertOpsTeam, region Global. Display name appears in notifications.
  • One action group can serve many alert rules.

Alert processing rules

  • An alert processing rule changes what happens after an alert fires, without editing each alert rule.
  • Suppress notifications: alerts still fire and are recorded, but no notification is sent. Good for planned maintenance.
  • The other main use is to add action groups to alerts in a scope.
  • It can run at a specific time or on a recurring schedule, and you choose the time zone.
  • Simple memory: action group = who is told. Processing rule = when they are told.
Part 2 · Exercise

Exercise

Goal: deploy a monitored VM, prove data is arriving, set up an alert and action group, add a maintenance suppression rule, then delete the VM to trigger the alert. About 45 minutes.

Lab names are kept: az104-rg11, az104-vm0, az104-dcr11, Alert the operations team, VM was deleted, Planned Maintenance. Do not delete the VM until Task 2 is done.

Task 1: Deploy the lab infrastructure

  1. Download \Allfiles\Labs\11\az104-11-vm-template.json. Sign in to the portal.
  2. Search for Deploy a custom template → Build your own template in the editor → Load file → select the template → Save.
  3. Fill in the form:
    • Resource group az104-rg11 (create if needed), Region East US
    • VM size Standard_D2s_v5 if available
    • Username localadmin, and a complex password
  4. Review + create, Create, wait, then Go to resource group.
  5. Confirm the group has: VM az104-vm0, a workspace starting az104-law11-, data collection rule az104-dcr11, plus the network, NIC, public IP, NSG and storage account.
  6. Open the VM. If it is Stopped, select Start and wait for Running.
  7. Settings → Extensions + applications: AzureMonitorWindowsAgent must show Provisioning succeeded.
  8. Open az104-dcr11 → Configuration → Resources: confirm the VM is associated.

If the size fails, redeploy to the same group with Standard_D2s_v6, then Standard_D2s_v7. If a partial deployment causes a conflict, delete az104-rg11 and restart Task 1.

Check: the VM is Running, the agent succeeded, and the DCR lists the VM.

Task 2: Verify monitoring data with Azure Monitor Logs

  1. Open the az104-law11- workspace → General → Logs. Close any welcome window or Queries hub. Use KQL mode.
  2. Run the Heartbeat query and confirm results contain az104-vm0:
    • Heartbeat | where TimeGenerated > ago(30m) | where Computer =~ "az104-vm0" | summarize HeartbeatCount = count(), LastHeartbeat = max(TimeGenerated) by Computer, Category
  3. No rows? Wait 5 minutes and rerun. Still none: recheck the agent extension and the DCR association.
  4. Run the performance query and confirm it returns data:
    • InsightsMetrics | where TimeGenerated > ago(30m) | where Computer =~ "az104-vm0" | where Name == "UtilizationPercentage" | summarize AverageUtilization = avg(Val) by bin(TimeGenerated, 5m), Computer | render timechart

Check: both queries return data. Continue only after that.

Task 3: Create an action group

  1. Portal → Monitor → Alerts → Action groups → Create.
  2. Basics: group az104-rg11, Region Global, name Alert the operations team, display name AlertOpsTeam.
  3. Next: Notifications: type Email/SMS message/Push/Voice, name VM was deleted.
  4. Select Email, enter your address, OK, then Review + create and Create.

Check: you receive an email saying you were added to the action group (it can take a few minutes).

Task 4: Create an Activity Log alert

  1. Monitor → Alerts → Create → Alert rule.
  2. Scope: select your subscription, Apply.
  3. Condition: signal Activity log, then Delete Virtual Machine (Virtual Machines), Apply. Leave Event level and Status as All selected.
  4. Actions: Use action groups, pick Alert the operations team, Select.
  5. Details: group az104-rg11, name VM was deleted, description A VM in the subscription was deleted, Region Global, enable on creation.
  6. Review + create, Create. Then Alerts → Alert rules and confirm the rule is enabled.

If the portal says Couldn't load metric query signals, try selecting the signal anyway. If you cannot apply it, use Cloud Shell (Bash): get the subscription ID and action group ID, then run az monitor activity-log alert create --name "VM was deleted" --resource-group az104-rg11 --scope "/subscriptions/$subscriptionId" --condition "category=Administrative and operationName=Microsoft.Compute/virtualMachines/delete" --action-group "$actionGroupId".

Check: VM was deleted shows as enabled under Alert rules.

Task 5: Configure an alert processing rule

  1. Monitor → Alerts → Alert processing rules → Create.
  2. Scope: your subscription, Apply. Next: Rule settings → Suppress notifications.
  3. Scheduling: At a specific time. Start today 10:00 PM, End tomorrow 7:00 AM, your time zone.
  4. Details: group az104-rg11, name Planned Maintenance, description Suppress notifications during planned maintenance.
  5. Review + create, Create.

If your current time falls inside the window, change the schedule first, or it will hide the email you are waiting for.

Check: the rule is listed and its schedule does not cover the current time.

Task 6: Trigger and verify the alert

  1. Confirm VM was deleted is enabled.
  2. Portal → Virtual machines → tick az104-vm0 → Delete.
  3. Type delete in the confirmation box, Delete (and again if asked). Watch Notifications until it is deleted.
  4. Wait for the email saying the VM was deleted alert was activated (a few minutes).
  5. Monitor → Alerts: find the alert, open it and review scope, condition, operation name, status and history.
  6. Optional: rerun the Task 2 queries. Data collected before deletion is still there.

Check: the email arrives and an alert named VM was deleted is listed in Alerts.

Cleanup: delete az104-rg11 (open it, Delete resource group, type its name, Delete). PowerShell: Remove-AzResourceGroup -Name az104-rg11. CLI: az group delete --name az104-rg11.

Good to remember for the exam

  • Metrics = numbers over time. Logs = records in a Log Analytics workspace, queried with KQL. Activity Log = control-plane actions in the subscription.
  • VM guest data path: Azure Monitor Agent + data collection rule (associated with the VM) + Log Analytics workspace.
  • Tables: Heartbeat shows the agent is alive. InsightsMetrics holds performance data.
  • VM deletion is an Activity Log event (Microsoft.Compute/virtualMachines/delete), not a metric.
  • Alert rule = scope + condition + actions + details. Types: metric, log search, activity log.
  • Action group = who is notified and what runs. Reusable across alert rules.
  • Alert processing rule = when. Suppress notifications for maintenance. Alerts still fire and are recorded.
  • Severity 0 = Critical, 4 = Verbose. Metrics kept 93 days, Activity Log 90 days.
  • Verify data is arriving before deleting the resource that produces it.

  1. What is the difference between metrics, logs and the Activity Log?
    Metrics are numeric values over time (like CPU %). Logs are detailed records stored in a Log Analytics workspace and queried with KQL. The Activity Log records subscription-level actions such as creating or deleting a resource.
  2. Which three things must be in place for a VM to send guest data to a workspace?
    The Azure Monitor Agent on the VM, a data collection rule associated with the VM, and a Log Analytics workspace to receive the data.
  3. What does a data collection rule do?
    1. Sends the email when an alert fires
    2. Defines what data to collect and where to send it
    3. Stores the logs
    4. Deletes old logs
    B. The DCR defines what is collected and the destination. The workspace stores the data, and an action group sends notifications.
  4. Which table would you query to prove the agent on a VM is alive?
    Heartbeat. InsightsMetrics holds the performance data.
  5. What does this KQL do? Heartbeat | where TimeGenerated > ago(30m)
    It reads the Heartbeat table and keeps only records from the last 30 minutes. The pipe (|) passes the result to the next step.
  6. The query returns no rows right after deployment. What do you do?
    Wait about five minutes and rerun it. If it still returns nothing, check that the agent extension succeeded and that the DCR is associated with the VM.
  7. You want an alert when anyone deletes a VM in the subscription. Which signal type?
    1. Metric
    2. Activity log
    3. Heartbeat
    4. Application Insights availability
    B. Deletion is an Activity Log administrative operation (Microsoft.Compute/virtualMachines/delete), not a metric.
  8. What are the four parts of an alert rule?
    Scope (what is watched), condition (signal and logic), actions (action group) and details (name, resource group, severity and so on).
  9. What is an action group, and can several alert rules share one?
    A reusable set of notifications (email, SMS, push, voice) and actions (runbook, function, Logic App, webhook, ITSM, Event Hub). Yes, many alert rules can use the same action group.
  10. You need to stop emails during a planned maintenance window without editing any alert rule. What do you create?
    1. A new action group
    2. An alert processing rule with Suppress notifications
    3. A new workspace
    4. A diagnostic setting
    B. An alert processing rule with a schedule. Alerts still fire and are recorded, but no notification is sent.
  11. In one line each: what does an action group decide and what does an alert processing rule decide?
    The action group decides who is told and what runs. The alert processing rule decides when notifications are delivered, or suppressed.
  12. After you delete the VM, can you still query the data it collected earlier?
    Yes. Records already in the workspace stay for the workspace retention period. The VM just cannot send any new data.
