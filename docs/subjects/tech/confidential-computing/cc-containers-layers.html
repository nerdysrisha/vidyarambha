Attestation Flow (How Secrets Are Released)
① Pod / enclave scheduledK8s schedules a confidential pod → Kata runtime (L3a) or direct EC2 spawn (L3b) creates the TEE.
↓
② Boot & measurecVM firmware boots, vTPM records measurements of kernel + initrd + container image hash into PCRs (L3a). NSM records PCR values directly (L3b).
↓
③ TEE evidence generatedAttestation agent inside TEE requests a signed Quote from hardware: TDX TDREPORT / SEV-SNP report / NSM attestation doc. Contains CPU identity + firmware version + workload hash.
↓
④ Evidence sent to L6 verifierEvidence sent over HTTPS to external Attestation Service (Veraison / MAA / IBM Attestation Svc). Verifier checks certificate chain back to CPU vendor root of trust.
↓
⑤ Policy checkPolicy engine compares measurements against trusted allow-list: expected code hash, firmware version, TEE mode enabled. Mismatch → rejected, secrets not released.
↓
⑥ Secrets releasedKBS releases encryption keys only now. CDH / attestation agent delivers them into the TEE. Container decrypts data-at-rest and establishes TLS for in-transit protection.

Key Rule
Secrets must never be released before attestation completes (L3→L6 flow). If the CSP operates the Key Broker Service (L6), the entire confidentiality model collapses — the trustee must be independent.

AWS Nitro (L3b) is a process-based enclave — it does not follow the cVM model. Forcing it into a cVM framing is technically inaccurate. L4b reflects this difference explicitly.
ANSSI conclusion: Confidential Computing is not a silver bullet. L3a (cVM) and L3b (process-based) are fundamentally different execution models — the same pod/container layer (L4) operates differently for each. Always attest the entire TCB chain L0→L6. Tie secret provisioning (L6) to attestation. Harden guest workloads (L3/L4) against hostile hypervisor inputs (L2). Code confidentiality is not guaranteed — the processor needs the workload unencrypted to start executing it. Physical and manufacturer attacks are out of scope for CC.
