How one CPU runs multiple encrypted VMs — cVM isolation explained

L0 hardware · L1 firmware · L2 hypervisor (untrusted) · TEE memory encryption · per-VM keys

L0 Physical hardware — one server, one CPU socket — root of trust · never splits · everything above depends on this ROOT OF TRUST

One physical machine. The CPU, DRAM, and Memory Encryption Engine are a single piece of silicon and metal. Nothing at this layer changes when VMs are created — the hardware just gains the ability to enforce per-VM encryption domains.

CPU die — Intel Xeon w/ TDX
64 physical cores. TDX (Trust Domain Extensions) module is etched directly into silicon. Generates per-VM AES-256 keys internally. Keys never leave the CPU die.
DRAM — Samsung DDR5 512 GB
Shared physical memory. All VMs share the same DRAM sticks. The TEE encrypts each VM's assigned address range so other VMs and the hypervisor only see ciphertext.
Memory Encryption Engine (MEE/TME)
Intel TME-MK circuit sits between CPU cache and DRAM bus. Automatically encrypts/decrypts memory lines using the key assigned to the active VM context. Transparent to software.

L2 Hypervisor / KVM + QEMU — UNTRUSTED — CSP controlled — slices CPU time + memory ranges into VMs · treated as actively hostile ⚠ UNTRUSTED

The hypervisor does what it has always done — assigns each VM a slice of CPU time and a range of physical memory addresses. This mechanism is unchanged by Confidential Computing. What changes is that for cVMs, the memory range assigned is immediately encrypted by the MEE using a key the hypervisor cannot access. The hypervisor can still read, write, and move memory — it just reads and writes encrypted bytes it cannot interpret.

Where do Key-A and Key-B come from — and where do they live?
Step 1 — Hypervisor calls TDX module (inside CPU silicon) to create a new Trust Domain (TD) for cVM-A
Step 2 — TDX module uses its internal PRNG (seeded from hardware entropy) to generate a 256-bit key — Key-A — entirely inside the CPU die
Step 3 — Key-A is loaded into a dedicated CPU-internal key slot (MKTME key table) — it never travels outside the CPU package
Step 4 — MEE circuit is configured to use Key-A for cVM-A's memory address range — all DRAM reads/writes for that range are auto-encrypted/decrypted
Step 5 — Same process happens independently for cVM-B → Key-B, different key slot, different address range
Step 6 — On VM shutdown — key slot is zeroed inside CPU — Key-A is gone forever, DRAM pages remain as meaningless ciphertext

4 things to understand
1
Hardware (L0) is always one piece. The CPU, DRAM, and MEE never split. The server chassis, the DRAM sticks, the CPU socket — all one physical object. Confidential Computing adds no new hardware.
2
Hypervisor slices — same as always. L2 assigns each VM a CPU time slice and a physical memory address range. This mechanism is identical to normal virtualisation — nothing new here.
3
TEE silicon adds per-VM encryption keys. When a cVM is created, the TDX/SEV-SNP circuit inside the CPU generates a unique AES-256 key for that VM. The MEE uses it to encrypt every DRAM write for that VM's address range — automatically, in hardware.
4
Keys never leave the CPU die. Key-A and Key-B live only in CPU-internal key slots. The firmware, hypervisor, OS, and application above never see them. They are zeroed when the VM shuts down.
Key properties
Algorithm: AES-256-XTS — tweakable block cipher, different ciphertext per memory address even for identical plaintext
Scope: one key per Trust Domain (TD) — cVM-A and cVM-B cannot decrypt each other's memory
Lifetime: ephemeral — generated at VM creation, zeroed at VM shutdown, never persisted to storage
Location: MKTME key table inside CPU package — physically inaccessible to any external bus or software
Key insights
Same hardware, different security domains. The physical DRAM chip holds bytes for both the regular VM and both cVMs. The MEE circuit determines which bytes are encrypted on the way out — purely based on which VM's address range is being accessed.
The hypervisor can still move memory. It can copy cVM-A's encrypted bytes to a different location. They remain encrypted — the key is bound to the VM identity, not the physical address. Moving ciphertext doesn't help an attacker.
This is enforced by silicon, not software. No software switch, no OS policy, no hypervisor setting controls this — the MEE circuit sits on the memory bus between the CPU cache and DRAM. There is no software path to bypass it.
Intel TDX vs AMD SEV-SNP
Intel TDX — uses MKTME (Multi-Key Total Memory Encryption). Each Trust Domain gets a KeyID. MEE selects encryption key based on KeyID tag on each memory page.

AMD SEV-SNP — uses SME (Secure Memory Encryption) with ASID-based key selection. Each VM gets an Address Space ID, mapped to a key in the AMD Secure Processor. Adds RMP (Reverse Map Table) to prevent hypervisor from remapping cVM pages.

Both achieve the same result: per-VM hardware memory encryption, keys held inside the processor, hypervisor sees only ciphertext.
Bottom line: The hardware (L0) is always one physical piece. The hypervisor (L2) slices it into VMs as it always has. The TEE silicon (TDX / SEV-SNP) adds one thing on top: a per-VM AES-256 key generated inside the CPU die, used by the Memory Encryption Engine to encrypt every byte of that VM's DRAM range. The hypervisor cannot read those keys — they never leave the CPU package. This is enforced by silicon, not by software.
