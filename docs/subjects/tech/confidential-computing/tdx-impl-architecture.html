Why peer-pod CoCo, not a whole-node TDX worker
Design rationale for the diagram above. Compare: worker node on a TDX VSI (node = 1 TD) vs. one TD per pod (peer-pod).
Whole-node TDX worker: one TD, one big TCB
Node OS + kernel (RHCOS), modules, eBPF
kubelet, CRI-O, runc/crun, CNI (OVN-K), CSI
Node agents: MCD, monitoring, logging, sshd/oc debug node
Pod A, Pod B, Pod C (all share the same kernel and TD memory)
Outside TD: cloud host / hypervisor only
Cluster-admin, node root and every co-tenant pod sit inside the trust boundary.
Peer-pod CoCo: one TD per pod, minimal TCB
Pod TD: minimal guest kernel + initrd (measured)
kata-agent (Rego policy), attestation-agent, CDH, image-rs
Only this pod's containers
Outside TD: worker node, kubelet, CRI-O, cloud-api-adaptor, cluster-admin
Outside TD: cloud host / hypervisor
The worker node is an untrusted relay (VXLAN 4789 + agent ttrpc). It cannot read pod memory.
1. Trust boundary: node TD protects against the cloud, not against your own operators
Whole-node TDX TDX encrypts guest memory (MKTME, AES-XTS) and blocks the host/VMM from reading it. But inside the TD, root on the node can read /proc/<pid>/mem, attach with ptrace/gdb, dump cgroups, or run oc debug node/<n> and chroot /host. Memory is "confidential" only from a party that never had access anyway.
Peer-pod CoCo The pod TD boots its own kernel. There is no node shell, no CRI-O, and no runc exec path into it. The only management channel is the kata-agent ttrpc API, and that API is filtered by an agent policy (see #2). Cluster-admin and node root are moved outside the TCB.
2. Kata agent policy blocks kubectl exec / cp / logs; a node TD cannot
Whole-node TDX kubectl exec goes API server → kubelet → CRI-O → container. All allowed, all standard. kubectl cp, logs, port-forward, ephemeral debug containers and crictl also work. Any RBAC grant (or admin compromise) exposes plaintext data in use.
Peer-pod CoCo The Rego policy is delivered via INITDATA (the base64+gzip box in the pre-flight row). It allow-lists agent RPCs such as CreateContainerRequest (with exact image digest, command, env, mounts) and denies ExecProcessRequest, ReadStreamRequest, CopyFileRequest. The policy digest goes into the attestation evidence, so tampering changes the measurement and KBS refuses to release secrets.
3. Per-workload isolation: kernel and TD per pod
Whole-node TDX All pods share one kernel and one TD key. A container escape (runc/kernel CVE, privileged pod, hostPath, CAP_SYS_ADMIN) lands in the node context and gives access to every other pod's memory and to the kubelet's credentials. Confidential and non-confidential workloads mix in the same failure domain.
Peer-pod CoCo Each pod is a separate TD (its own kernel, its own memory key, its own IBM Cloud VSI, here bx3dc-2x10). An escape only reaches that pod's guest. Blast radius = one pod. Untrusted and confidential pods can coexist on the same cluster, selected by runtimeClassName: kata-remote.
4. Attestation granularity: per pod, bound to what is actually running
Whole-node TDX One TDX quote covers the node boot chain (MRTD, RTMR0-2: firmware, bootloader, kernel). After boot, kubelet pulls arbitrary images and starts arbitrary pods, and none of that is reflected in the quote unless you build IMA/RTMR extension yourself. A verifier cannot answer "which image and config is this secret going to?"
Peer-pod CoCo The attestation-agent (amber box in the pod VSI) fetches a TDX quote (via configfs-tsm) including the initdata hash. Trustee's Attestation Service verifies the quote against Intel collateral (PCS/PCCS) and compares measurements to reference values (RVPS). Only then does the KBS issue a token and release the key. Secrets are bound to a specific pod measurement.
5. Image pull, verification and decryption happen inside the TD
Whole-node TDX CRI-O/containerd pulls and unpacks layers on the node. Layer contents are in node page cache and on node disk (encrypted only if you added LUKS). No mandatory signature check, and encrypted images (ocicrypt) require the node itself to hold the private key, which admins can read.
Peer-pod CoCo image-rs in the guest pulls directly from the registry, enforces the signature policy (cosign / simple signing) and decrypts layers using keys fetched from the KBS through the Confidential Data Hub. Layers live only in guest-encrypted memory. The worker never sees plaintext layers.
6. Secrets: Kubernetes Secrets are readable by admins, KBS resources are not
Whole-node TDX K8s Secrets live in etcd (base64), are mounted on the node as tmpfs, and are visible to anyone with get secrets or node access. Placing a node in a TD does not change who can read them at the API layer.
Peer-pod CoCo CDH fetches secrets from the user-provided Trustee KBS (red box) after successful attestation, over HTTPS, and exposes them as sealed secrets or KBS resource URIs. They never transit etcd or the kubelet. Because you own the Trustee (Ubuntu VSI in the same VPC), you hold the release policy and the key custody.
7. Attack surface in the TCB: general-purpose node OS vs. purpose-built guest
Whole-node TDX The TCB includes a full RHCOS userland, systemd, container runtime, CNI plugins, device plugins, node agents and their update channels (MCO rolls new OS/config onto the node at any time). Every component and every operator action can alter what runs inside the trusted environment.
Peer-pod CoCo The pod VM image (RHEL9/RHCOS PodVM image in the pre-flight row) is small, immutable and measured. It has no sshd, no general shell path and no package manager at runtime. The set of processes inside the TD is deliberately tiny: kata-agent, attestation-agent, CDH, plus the workload.
8. Why not "TD-per-pod on a TDX worker" (classic Kata/CoCo)? Nested virtualization
Constraint Classic Kata launches each pod with QEMU/Cloud-Hypervisor+KVM. The ROKS worker is already a VSI (a guest), and a TD cannot host another TD: there is no nested TDX. So kata-qemu-tdx only works on bare metal TDX hosts, not inside a VSI worker.
Peer-pods workaround cloud-api-adaptor (purple box on the worker) skips local virtualization. It calls the IBM Cloud VPC API (API key / trusted profile) to create a TDX-enabled VSI per pod, then wires it back to the worker via VXLAN 4789 so the pod still looks like a normal pod to Kubernetes.

Honest trade-offs of peer-pods (and when a TDX worker is enough)
Costs of peer-pods Slower pod start (a VSI is provisioned per pod, typically tens of seconds). Extra VSI cost per pod and quota limits per profile/region (TDX only in us-south, us-east, eu-de). Fixed VM size per pod (bx3dc-2x10) instead of bin-packing on a node. Extra moving parts: cloud-api-adaptor credentials, PodVM image lifecycle, and a Trustee you must run and secure. Networking and storage integration is more limited than for regular pods.
Whole-node TDX is enough when The only adversary is the cloud provider, and you fully trust your own cluster admins, SREs and every workload on the node. You want lift-and-shift with no per-pod latency or VSI overhead. Compliance requires "encrypted in use at the infrastructure level" and not "operator cannot access". If the requirement is operator cannot access data in use, peer-pod CoCo is the only one of the two that meets it.
